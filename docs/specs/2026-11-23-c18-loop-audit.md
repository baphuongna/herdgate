# Spec C18 — Cycle audit: guardrail bằng cơ chế, không chỉ bằng lời

Ngày: 2026-11-23 · Vòng: DEV-LOOP (worktree `c18`, branch `c18-loop-audit`) ·
Chủ đề: guardrail của loop thành cơ chế đối chiếu git sau mỗi vòng.

## Bối cảnh (bằng chứng)

- Guardrail "không publish/tag", "không bump version", "không in token" hiện
  chỉ là **LỜI trong prompt** (`docs/DEV-LOOP/AUTO.md`). Đã có 1 vi phạm thật
  (in room token ra output) và nó chỉ được phát hiện **vì agent tự khai** —
  không có bằng chứng độc lập.
- Cần cơ chế: sau mỗi vòng của loop, đối chiếu git của `cfg.cwd` trong window
  thời gian của vòng với các luật trên, ghi kết quả vào `loop.log`; nếu có
  vi phạm → loop **ngừng nuôi** agent đó (không nudge nữa) cho tới khi owner
  `resume`.

## Tính năng

1. **`plugin/loop/server/audit.mjs`** (file mới — chỉ export, KHÔNG CLI,
   import tự chứa: `node:*` và `./boot.mjs` thôi):
   `auditWindow({ cwd, since, until })` → `{ ok: true, commits, tags, violations }`:
   - `commits`: `git -C cwd log --since --until --format=%H%x00%s`
     (spawnSync, timeout 10s/lệnh, env sạch kiểu git-safe +
     `GIT_CONFIG_NOSYSTEM=1`; chỉ đọc nên không hooks, không index lock).
   - `tags`: `git for-each-ref --format=%(refname:short)%00%(creatordate:unix)
     refs/tags` → giữ tag có creatordate ≥ since.
   - Luật `version-bump`: với MỖI commit trong window, `git diff-tree -p <sha>
     -- package.json plugin/herdr-plugin.toml plugin/mirror/herdr-plugin.toml
     plugin/loop/herdr-plugin.toml` → dòng khớp `^[-+]\s*"version"\s*:` hoặc
     `^[-+]version\s*=` → violation `{rule:"version-bump", sha, subject}`
     (mỗi commit tối đa 1 violation).
   - Luật `tag`: tag mới trong window → violation `{rule:"tag", name}`.
   - Luật `token`: `git log -p --since --until` → chỉ dòng THÊM (`^+`,
     không phải `+++`) khớp `/HERDGATE_(ACCOUNT|ROOM|BRIDGE)_TOKEN\s*=\s*\S{8,}/`
     hoặc `/"deviceSecret"\s*:\s*"[^"]{8,}"/` → violation
     `{rule:"token", sha, line}` — **TUYỆT ĐỐI không chứa giá trị token**
     trong output/log: chỉ sha + số dòng trong file mới (số dòng tính từ hunk
     header `@@ -a,b +c,d @@`).
   - git lỗi / timeout / không phải repo → `{ ok:false, error }`
     (error ngắn ≤ 120 ký tự).
   - Tổng thời gian ≤ 30s (deadline); mọi lệnh read-only (`log`,
     `for-each-ref`, `diff-tree`) — không `git gc`, không `reset`, không đụng
     index (`GIT_OPTIONAL_LOCKS=0`).
2. **Tích hợp `cmdEvent`**: sau settle hợp lệ (armed, running, không paused)
   và TRƯỚC nudge → `auditWindow({cwd: cfg.cwd, since: s.lastAuditAt ??
   s.startedAt, until: Date.now()})`; lưu `s.lastAuditAt = until`.
   - ok + không vi phạm → log `AUDIT ok commits=<n> tags=<n>`, nudge tiếp.
   - Có violations → log `AUDIT VIOLATION <rule1>,<rule2>`,
     `saveState({...s, lastAuditAt: until, auditHold: {rules:[...], at}})`,
     **KHÔNG nudge**, exit 0. Các settle sau đó cũng bị giữ (auditHold chặn
     trước khi audit chạy lại) cho tới khi owner `resume`.
   - `ok:false` (lỗi hạ tầng) → log `AUDIT error <error>`, **KHÔNG chặn
     nudge**. Lý do fail-open ở đây: lỗi git/timeout **không phải bằng chứng
     vi phạm** — chặn loop vì máy git hỏng là dương tính giả vô hạn. Window
     lỗi KHÔNG được đánh dấu đã audit (`lastAuditAt` giữ nguyên) để settle kế
     audit lại trọn window đó.
3. `resume`: xoá `auditHold` (owner đã xem xét). `status`: lộ `lastAuditAt`,
   `auditHold` trong `state`.

## Tiêu chí nghiệm thu (đo được)

1. `auditWindow` trực tiếp (repo git tạm):
   a. window sạch → `{ok:true, violations:[]}`;
   b. commit đổi `"version"` package.json → đúng 1 violation `version-bump`
      với sha + subject khớp;
   c. tag creatordate trong window (GIT_COMMITTER_DATE) → violation `tag`;
   d. commit thêm `HERDGATE_ACCOUNT_TOKEN=abcdefgh12345` → violation `token`;
      `JSON.stringify(result)` **KHÔNG** chứa `abcdefgh12345`;
   e. cwd không phải repo → `ok:false`, error ≤ 120 ký tự.
2. Tích hợp `cmdEvent` (stubHerdr, repo tạm có violation): exit 0, KHÔNG có
   `pane.send_text` trong calls, state có `auditHold`, loop.log có
   `AUDIT VIOLATION`.
3. `resume` xoá `auditHold`; `status` trả `lastAuditAt` + `auditHold`.
4. File audit.test.ts xanh tuyệt đối qua
   `node --test test/loop-audit.test.ts`; test cũ `loop-plugin.test.ts` vẫn
   xanh (không regress). KHÔNG chạy full suite (ràng buộc vòng này —
  controller chạy lúc merge).

## Thiết kế

- `audit.mjs`: helper `gitRun(args, cwd, deadline)` — spawnSync `"git"`
  (không shell), timeout = min(10s, budget còn lại), env scrub
  `{PATH, HOME, LANG, GIT_CONFIG_NOSYSTEM:1, GIT_OPTIONAL_LOCKS:0}`, buffer
  8 MiB. Deadline tổng 30s — vượt budget → `ok:false` (fail-open như lỗi
  hạ tầng, có log `AUDIT error`).
- Window: `since`/`until` epoch-ms → ISO 8601 UTC cho `--since/--until`
  (giây lẻ của epoch ms không quan trọng: vi phạm nào cũng đi kèm commit/tag
  thật, chênh <1s không bỏ sót vì window kế quét lại từ `lastAuditAt`).
- `index.mjs`: kiểm tra `auditHold` ngay sau check `paused`; audit đặt sau
  check paused và TRƯỚC nhánh maxCycles/cooldown — vẫn đúng "trước nudge",
  và phép chốt cuối cùng chuyển `done` (maxCycles đạt) vẫn được audit
  (nếu audit chỉ chạy ngay trước nudge thì vòng cuối của loop maxCycles
  thoát khỏi audit — lỗ hổng của cách đặt thứ hai).
- Nudge path thêm `lastAuditAt: until` vào saveState sẵn có (không ghi
  state hai lần).

## Rủi ro

- Repo lớn / nhiều commit → budget 30s cạn → `ok:false` fail-open có log
  (không treo event hook — giới hạn cứng của herdr plugin hook).
- Commit gộp (merge) hiển thị combined diff — dòng `+` vẫn bị quét token
  (cách xử lý đúng: token trong merge patch cũng là vi phạm).
- Root commit (không parent) `diff-tree -p` in gì đó → thêm version
  trong commit đầu KHÔNG bị tính là bump (không có dòng `+version` so với
  parent; chấp nhận: bump có nghĩa là so với bản trước).
- `git log -p` stdout chứa patch thật — KHÔNG BAO GIỜ echo stdout ra
  log/stdout; chỉ parse và phát violations dạng sha+số dòng.
- Chỉ audit commit trên nhánh hiện tại của cwd (không `--all`) — đủ cho
  guardrail vòng (agent làm việc trên nhánh checkout của cwd).

## Ghi chú cho reviewer

- `lastAuditAt` KHÔNG tăng khi audit `ok:false` (khác mô tả thô "lưu luôn"):
  lý do — không có bằng chứng thì window đó phải được audit lại ở settle kế;
  tăng `lastAuditAt` sẽ ăn mất window lỗi.
- Việc ngoài phạm vi phát hiện: không có. (Nếu merge: ví dụ audit cũng nên
  quét `docs/DEV-LOOP.md` Cycle Log thì cần luật riêng — để vòng sau.)
- Đề xuất vòng sau: khi `auditHold`, một action riêng để owner xem CHÍNH XÁC
  commit/tag nào vi phạm (hiện chỉ xem qua log AUDIT VIOLATION + git tay).
